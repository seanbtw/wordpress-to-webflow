# Verification

The aim: no difference a user would notice, no URL lost, no behaviour missing, and proof of each. Verify the pages that produce the traffic first and strictest (Search Console tells you which).

## Measuring

**Differences are found by measuring and by comparing code, never by comparing pictures.** A picture comparison says that something differs and not what; it passes a wrong value that happens to look close, and it cannot be rerun as a test. The measurements are: computed styles and boxes per element (`scripts/measure-blocks.mjs`), the order of sections and headings per page (`scripts/heading-sequence.mjs`), text, link and media sets (`scripts/compare-bodies.mjs`, `scripts/crawl-links.mjs`), and head tags (`scripts/seo-check.mjs`, `scripts/code-parity.py`). Screenshots may be kept as a record for the person reviewing. A picture has one working use: to find *where* to measure. The whole-page sweep (next section) lays two parts over each other to locate the places that differ, then reports the measured values at each place; the picture is never the verdict. A part the sweep lists for its pixels alone, with no measured value differing, is not yet a finding: it has to be explained (a different slide, a resampled image) and counted.

- **Measure against the local WordPress at the same width, both sides of every breakpoint.** The reference measurements are recorded at five widths (390, 768, 1200, 1440, 1920); block and page comparisons also run at each breakpoint and the pixel below it: 479/480, 767/768, 991/992 and each of the theme's further steps (for example 1199/1200). This caught wrong breakpoints, missing steps, a line-height coming from an inline span, a slider overriding widths, clamp and paragraph sizes, tag padding and button geometry.
- **Use the theme's own numbers** (compiled CSS, block options) as the expected values, and the browser's computed values on both sites as the measurement.
- **Force lazy images eager and decoded** before measuring or capturing.
- **Keep block order equal to the reference page's** when measuring a block in isolation; some theme behaviour depends on neighbours.
- **Measure every element that has its own text, media, a background, a background image or a border**, paired by position in document order. A walk that only looks at text passed an icon button with the wrong background. Walk through zero-size wrappers (`<picture>`, an inline link): their children are visible.
- **Scroll instantly.** Themes set `scroll-behavior: smooth`; a block scrolled into view smoothly is still moving when its boxes are read.
- **Cache-bust the Webflow side only, and not on pages whose scripts read the query string.** A query parameter on the WordPress side can change the page (a listing that reads every parameter as a filter), and a rebuilt listing that copies that behaviour does the same on the Webflow side: one showed "All filters (1)" for the cache-buster alone.
- **Count a button as one item on both sides.** A theme button is one element; its Webflow replacement may be a link plus a label span, which shifts every later pairing. Treat anything pill-shaped, and whatever `checks.measure.oneItemSelector` names, as one item: its box, its label's type and its colours.
- **Measure phones with a phone user agent** as well as a phone width, for themes that choose markup on the server.
- **Measure whole templates.** Give the measurement the template's whole content wrapper. A template measured on one block looked finished while three sections were missing from every item.
- **A large mismatch count after a small change is usually one shifted pairing**, not thousands of faults (82,945 checks gave 26,568 mismatches after one element lost its box to `display: contents`). Fix the first mismatch and rerun before reading the rest.

## The whole-page sweep: no samples

**Every page and every item is compared with WordPress, whole, at phone, tablet and desktop widths. This is a required step, not something to run when someone asks.** `scripts/page-sweep.mjs --all` does it: it splits each page into its parts (the direct children of the main content wrapper, then the footer), pairs them in order, and for each pair reports a part missing or extra, a different height, and the measured values that differ under each place the two parts do not match (tag, font, size, weight, line height, colour, padding, margin, border, gap, display). `triage.md` then groups every difference by cause, the staging element and the property, by the number of pages it shows on, so one fix clears one row.

Why it is required. Block specs prove the blocks they name, and a template example proves that one item. On the third build 27 specs were measured (45,708 checks at the phone width alone), every mismatch was explained, Phase 7 was signed off, and the owner then found differences by looking at pages. The first sweep, two thirds of the way through the site, had 375 of 863 parts differing, most of them the same few causes repeated across dozens of item pages: article bodies whose size, weight, colour and paragraph spacing no spec had measured, a related-items grid, image wrappers. The two earlier builds were signed off the same way and had never been swept. **A sample is a check that did not run on the rest.**

- **Run it as soon as the first template is published** (Phase 4), again after every release of scripts or styles, and as a Phase 7 gate. Early, it costs minutes and finds a cause once; late, the same cause is on every item.
- **Fix missing and extra parts first** (the second table of `triage.md`). Parts are paired in order within their group: bars with bars, content with content, the footer with the footer. One content part missing on staging still shifts every content pair after it on that page. A bar listed as missing on one side shifts nothing, and is usually a selector in `checks.sweep.bars` that matches on one side only: on one build the report named the footer as missing on a listing page, and a browser showed the footer and the filter bar there on both sides, the same size; staging's bar simply lacked the attribute the selector asked for. Measure before believing a missing part. Test the bar selectors in a browser on every page type that has a bar, on both sides, at a phone and a desktop width, before the first whole-site run: checked on the first template only, three of one build's bars matched on WordPress alone (a filter bar without its hook on one listing, a share bar whose attribute had been renamed by the compile step, a phone-only switch). The run's summary lists the pages where a bar matched on one side.
- **The triage counts one result per page and width, the newest.** The results folder keeps every run. Results saved under another name (the same page asked for with and without its closing slash) and results for pages since removed or excluded were once counted in, and nearly doubled a run's totals (1,027 results for 568 page loads). The script now leaves them out and says how many; a total that does not match the run's page loads is the sign to look.
- **A load the run could not compare is left out of the triage, not filled from an older run.** The sweep writes the loads with no result to `sweep/not-compared.json`, and the triage drops any earlier result for them. Before this, a page that hung at all four widths was still counted from the results of two runs earlier: the summary said 564 loads and 370 parts, the triage 568 and 379. The two files now give the same counts; if they do not, find out why before quoting either.
- **Then read the causes from the top.** Fix the cause on the most pages, rerun, and only then read on: later rows are often the same fault seen from a parent element or a shifted neighbour.
- **The first run is loud.** That is the point; do not raise the threshold to quieten it. A row that is truly not a fault (text that wraps one word differently, a third-party embed that draws itself) goes in `accepted-differences.md` with its reason.
- **The header and any floating bar are parts of their own.** The header is compared first, as it sits at rest. A sticky in-page menu, or any other bar that floats over the page, must be named in `checks.sweep.bars`: otherwise the sweep looks through it to read the page beneath, and its own colours and type are never read. A menu toggle was the wrong shade of black on every page of one site for that reason, through nine sweeps.
- **It compares pages at rest.** Hover and focus states, open menus and panels, sliders part-way through and anything behind a click are not in it; those belong to the behaviour checklist, which should measure the opened state the same way.
- **It needs the local WordPress copy running and every staging path in `staging-paths.json`**; rerun `staging-paths.mjs` after publishing new items, and read the line that says how many page loads were compared.
- **Account for every differing part.** After the last run, every part still listed sits in a named group in `accepted-differences.md`, with its count of parts and pages and the reason (a fault of the old site, a decision, a third-party embed, a slider caught on a different slide, a tool limit). The groups add up to the total. "Clean" means that and nothing looser: on the third build a first claim of clean still had 479 of 1,559 parts over the threshold, and grouping them turned up one more real fault.
- **Do the account by script, and make the script strict.** With hundreds of parts left, label each one from the sweep's own JSON: the accepted difference whose mechanism every one of its spots shows, or "open" with the values that differ. Four rules keep the account honest. It counts a part as differing by the sweep's own rule, text colour included, so its total equals the triage's (one account said 297 against 299: the two it lacked were under the pixel threshold and listed for a colour). A label covers a named part, never a whole page: "everything on the form page is the form swap" would also pass a broken footer there. A part gets a label only when every spot fits it. And "the same picture drawn differently" needs the same file on both sides. The gate is zero parts open, not a low number.
- **A run on a few pages writes its own summary** (`summary-partial-<time>.md`) and leaves the last full run's `summary.md` alone, so the evidence for the full run is never overwritten by a spot check.
- **Text that has lost its colour can be invisible, and barely moves the pixel count.** On one site a heading and two paragraphs were white on white: the editor had set them black with an inline colour inside a light-text container, and the build dropped the colour. The parts differed by 1 to 4 % of their pixels, the size of a resampled photo, and the measured value (`color: rgb(0, 0, 0) → rgb(255, 255, 255)`) sat in the sweep's results through several rounds of grouping before anyone read it. So the sweep now lists a part whenever the colour of some text differs under a region, whatever its pixel share, and `triage.md` counts those first. Read that row before anything else, and never put a part with a colour difference in a "pixels only" group.
- **Check every inline colour directly as well.** List each element the old site colours with an inline style, on every page and in every item body, and compare its computed colour and the background behind it on the new site. Report how many were compared.
- **Most of what is left after the fixes differs in pixels alone.** When the second build was swept, about 60 % of the differing parts were the same image file resampled, a slider on another slide, or text with identical values whose glyphs land a fraction of a pixel away. `triage.md` opens with a count of differing parts by kind, sorted from the measurements (shape, a value, another picture, the same picture, text). Start the account there, and name each group by what was measured, never by eye.
- **The triage splits the text colour row in two.** "The same text is a different colour" comes first: on one site all 12 such parts were real faults. "The two texts under the spot are not the same" comes second: the point landed on two different elements, and each text has to be measured again on both pages (of 389 such regions on that site, the 80 checked on ordinary pages had equal colours; on another site 355 such parts held 26 real faults). Neither row is dismissed by its count.
- **It splits "a measured value differs" the same way.** Where every differing spot in a part has a different text on each side, the point landed on two different elements, and the size or colour compared belongs to two different things. Those parts are listed apart (60 of 178 on one run). Match the texts and measure each on both pages before calling it a fault or a pairing: on seven such parts every matched text had the same size, line height, colour and alignment.
- **A tool that counts visible text must check the text is on screen.** With overflow visible, slider cards past the right edge of the viewport are laid out and not hidden; a colour lookup that tested only size and visibility found them on one side and not on the other.
- **A text colour row built on a wrong pairing is not a colour fault.** Where the two sides do not line up (an item type with no page on the old site), the row fills with pairs of two different texts. Measure the same text on both pages before believing or dismissing each one: on one site 355 such parts held 26 real faults.
- **Known limit: parts are paired in order, not by content.** Where one side prints an extra or an empty part (an item type that renders an empty page on the old site), every later pair on that page is wrong and every property "differs". Fix or accept those first. And below a part whose height differs, the probes land on unrelated elements: the height difference is the finding, the values under it are not.
- **A slider that sets its own height must measure again when the fonts arrive, and without rounding.** On the new site, a slider equalised in the fallback face was a line taller on some loads (+28 px): call the equalise step again on `document.fonts.ready`. One that read `offsetHeight`, which rounds, came out a tenth of a pixel short of a library that sets a fractional height: read `getBoundingClientRect()`.
- **One page that hangs the capture must not hold the run.** The sweep gives each page load a time limit (`checks.sweep.loadTimeoutSec`, default 300): a load with no result by then is closed and listed under "Not compared", and the run goes on. Before the limit existed, one page hung the capture browser on the last load of 1,239 and the run sat for three and a half hours with nothing written; the process was alive, so a waiter that watched only for it to end waited too. Watch the age of the log as well as the process, and run a page that hangs alone to see where.
- **A page that hangs at every width is a fault in the capture, to find, not a page to leave out.** One page was never compared in two whole runs. Its grid added 75 lazy images inside hidden filter panes half a second after the capture had scrolled; they never loaded, and the wait for every image to decode never ended. The sweep now waits a second after the scroll, switches late lazy images to eager and gives each decode five seconds. When a page still hangs, run it alone with a short `checks.sweep.loadTimeoutSec` and count, in a browser, the images whose `decode()` has not settled.
- **A result that changes from run to run is the page, not the build.** Run one page three times before trusting a small height difference. A slider or equal-heights script that measures itself before the fonts arrive keeps a height one line short on some loads only (24 px on two parts of one page, in about half the runs). A resize event makes it measure again: put `(async()=>{window.dispatchEvent(new Event('resize'));await new Promise(r=>setTimeout(r,1500))})()` in `checks.sweep.prep` for that side. On the test page that gave the same result three runs in three; it also moved one band by half a pixel, which shows as two small pixel-only rows with no value behind them, so use it where the height comes and goes and not everywhere.
- **Apply an accepted difference before measuring, not after.** A credit line the new footer leaves out on purpose made the footer "differ" on every page of one site. `checks.sweep.prep.wp` and `.wf` run a line of script on that side before it is measured, so the accepted difference stops flagging everything below it. Each use is listed in `accepted-differences.md`.
- **A host under a long parallel run refuses the odd request.** Over about 4,500 staging page loads, four were refused (403, 500, a timeout) and each answered on the next try. The script tries a refused load once more before listing the page as not compared; a page still listed after that is worth a look in its own right.
- **A long run can be picked up**: `--resume` skips every page and width that already has a result file. One full run stopped a quarter of the way through when the session's sign-in lapsed.
- **Known limit: lazy images can paint blank in the full-page capture of the old site**, though they are loaded and visible in the page. It shows as pixel differences with equal heights and no measured value differing. Name that group and count it; do not call it a fault and do not wave it through unexamined. Capturing in viewport-height slices is the likely cure and is not in the script yet.
- **A slider or gallery caught on a different slide** on the two sides gives the same signature (pixels differ, values equal, the image file differs). It was the largest group on the third build: 278 parts on 92 pages.

## States the sweep cannot see

The sweep compares pages at rest. On the third build everything below was found by eye or by a later pass, after the at-rest measurements were equal. Each is checked against WordPress the same way: the same state on both sides, values compared.

- **Open states, measured, at phone, tablet and desktop.** Open every menu panel, mega-menu column, sub-menu, search overlay, drawer, dropdown, share menu, accordion row and map view on both sides and compare boxes and type. "It opens" is not the check: a profile drawer passed the behaviour suite because it became visible, while rendering unstyled in the page flow below the footer. One fault showed only at the tablet width (a padding written at the phone breakpoint alone), so measure all three.
- **Hover and focus.** For every interactive element compare what changes on hover (which properties, to what, and how long the transition takes), the cursor, and whether Tab reaches it. Parent-hover effects are the usual loss: an arrow meant to appear when its link is hovered showed always, and a fade ran in 150 ms where the theme's took 500.
- **Three ways these checks fool themselves.** Hover the element that owns the effect and wait for its transition to finish before reading (a parent-hover blur read too early looked missing on both sides). Leave out visually hidden labels when listing an open panel's text (a one-pixel screen-reader label looked like a duplicated button). Measure the element a visitor sees, not a clickable overlay inside it (an overlay link sat inside a button's border and measured 2 px smaller).
- **A fix taken from one device is checked against the old site at every sweep width before it ships.** A row of slider dots was hidden after a look on one tablet ("the old site draws none"); the sweep later measured the old site drawing it at every width below the desktop step.
- **Keyboard.** Enter and Space on every toggle. A menu script bound its click to the `button` inside each item; the rebuilt item was a link with a button role, so hover opened it and neither a click nor Enter did, and a phone worked only by accident. Space activates a real button but not a link with a button role unless the script handles it.
- **The Tab order, not only "does Enter open it".** Walk the first 30 Tab stops of each template on both sides, with reduced motion on (autoplay otherwise changes which slide can be tabbed to). Two differences only a Tab walk showed: the old slider was itself a Tab stop that answered the arrow keys and its replacement was not, and a disabled control rebuilt as a link stayed in the Tab order, because a link ignores `disabled`.
- **A slow drag on every slider**, both sides: 45 % of a slide over half a second, and a short 12 % drag. A replacement slider library brings its own defaults; one needed half a slide where the original moved on any drag past 3 px, so slow drags sprang back. **Drag two sliders in a row and check nothing else opened**: the slider cancels the click after a drag, but a page-wide click handler that ignores a cancelled click opened a drawer on every drag across a card.
- **Scroll beside every open overlay.** The theme locked the page while a drawer was open; the rebuilt drawer did not, and the page scrolled behind it.
- **A rule that compensates for something unexplained is marked as such and looked at again.** A gap rule added to make one band line up was hiding an empty heading that should not have been printed; fixing the heading made the rule wrong. Twice in one night a fix for one page changed a converter rule that then moved another page: after changing a rule, re-check every stored body against it.
- **Run the whole behaviour suite after every fix release, not only the sweep.** A fix to one slider's start-up silently stopped another's autoplay; the sweep runs with reduced motion and could not see it. A run of single checks must never overwrite the full suite's report.

## Structure checks on every page

Greps and counts over the published HTML of every page, run after each insert and each release. Each one below would have caught a fault that reached review.

- **Every page that should answer has the theme's page shell**: its main content wrapper, between navigation and footer. Four collection templates were built with navigation and footer only; the rule that pads the content below a fixed header had nothing to pad, and the header covered the top of the footer on 61 pages.
- **Block names come from a data attribute, not from class names.** A compiler that names a style by what it looks like gives two different blocks the same class, and gives a plain wrapper inside a block the block's own class. A section-sequence checker that read block names from classes reported an extra block on 14 of 28 pages that were in the right order; reading the block name the compiler stamped on each block root gave 27 of 28. Before trusting the stricter reading, confirm on the heaviest pages that every block root carries the attribute, or nested blocks go uncounted.
- **Every script-driven block has its hook, on every instance, and has started.** List what each module looks for, per page and per template, confirm each is there, and confirm the library's own "initialised" class is present. A block re-inserted after the hooks were added, and a second instance on the same page, both stayed frozen stills. On a sister site a card template missing one image hook left every related image blank.
- **One of each widget.** Count them on both sides. A static copy of a control that a script also builds gave two overlapping map toggles.
- **Every link and button has the same name for a screen reader.** No other check reads it. A theme's buttons carried a hidden prefix, so a link read "Case Studies View our projects"; the rebuilt button was named by an `aria-label` holding the visible words only. About 17 names on 10 pages had lost their prefix, and nothing measured or compared showed it. For every link and button on both sides, compare the accessible name (hidden text, `aria-label`, image alt), in order.
- **Every link is right in the page's own HTML, before any script runs.** A share link printed one item's address on every item page; a script corrected it in the browser, so every rendered check passed. Read the published HTML of two items of each template and compare each link's address with WordPress's.
- **No converter placeholder and no default text in any published page.** `scripts/leftover-text.mjs --all` reads every page's own HTML for the HTML builder's `##INLINE` tokens and for Webflow's default text and labels, hidden elements included: one site had "This is some text inside of a div block." in a pill that shows only on hover, read aloud by a screen reader on every card. Add the compiler's own tokens and any sample name used while building to `checks.leftovers.extra`. It also counts Webflow's sample search results, which a site with no plan prints on its search page: expected until the plan is bought, and to be zero when the check is run again after cutover. Run over three sites it also found two things nobody had looked for: a Webflow sample result printed on a search page, and a question on the old site whose answer was sample Latin. The second is the old site's own fault, carried over faithfully: it goes to the owner, since the build writes no copy.
- **No text that cannot be read.** `scripts/colour-check.mjs --all` compares every inline colour on the old site with the same text on the new one, and measures every text on the new site against what is behind it; anything under 1.5:1 that the old site shows readable is a fault. Text that got harder to read but stays above that is the sweep's text colour row. Tested by turning one paragraph white on a white band: reported at both widths, exit code 1.
- **Every listing draws its cards from the CMS.** For each listing page, count the cards the published HTML marks as collection items (`w-dyn-item`) and require the number WordPress shows; a count of 0 means the cards are a static copy. The WordPress number is the total over every page of the listing (walk `/page/2/` onward, or press every Load More), since the old site usually pages on the server while the new list holds every item and a script pages it. Take the WordPress card selector from a check that already passes, and treat a WordPress count of 0 as a wrong selector, never as a pass. Where the CMS count is higher than WordPress's, find out why before accepting it: on one build 15 extra items were stubs kept in the same collection for the filters and removed by the page's script, which only a count in a browser after every Load More could settle (same names, same order, both sides). On one build the page-preparation step compiled all five listings as copies of the old site's cards. Every per-page check passed, because a copy matches the original exactly on the day it is made, and the site would never have shown a new article. It surfaced only because a script that builds the "related" band from listing cards found none. A page that compares perfectly has not been shown to be editable.
- **A list prints the same items as WordPress, hidden ones included.** For each list, compare the set of items in the page's HTML on both sides, not only the ones a visitor sees. A block that showed one category of questions on the old site was built as a list of every category with the others set to `display: none`: the page looked right and measured right, and carried five categories of text nobody could see, a sample answer among them, for search engines to read. It was found by the leftover-text check, which reads HTML, not by any check that looks at the rendered page. Filter the list at its source.
- **Every class a script creates has a rule in the stylesheet.** Grep the modules for the class names they add (`className =`, `classList.add`, template strings) and require a rule for each. Two modules were ported without their CSS: a drawer rendered unstyled, and two maps were 0 px tall.
- **Every item address answers as WordPress answers it.** Compare the status per item, not per collection: twenty items that exist only as a name were "Page not found" on WordPress and an empty page on staging.

## The Phase 7 checks

1. **Structure**: component sequence per page equals the composition map, by script. The script must read the marker *this* build writes on each block (a data attribute, or the compiled class name). One written for another build's markers finds nothing and never truly runs; print how many pages and blocks it compared.
2. **Measured layout**: every static page and template example measured whole against the local WordPress at 390, 768, 1200, 1440 and 1920 and both sides of each breakpoint, plus each fixed or sticky layout at a defined scroll position; the heading-order crawl over every path. **Triage by page height difference first** (lost or added content), then by the first mismatch on each page. Zero mismatches, or each one in the accepted-differences file. **Then the whole-page sweep over every path** (`scripts/page-sweep.mjs --all`, section above): its triage empty, or every row left in the accepted-differences file. The specs alone do not pass this check.
3. **Behaviour and accessibility**: the behaviour checklist, every line ticked with width and browser, including real Safari and iOS Safari. Menus, search, forms, sliders, accordions, filters, sticky elements, modals, maps, keyboard focus, reduced motion. Then the states the sweep cannot see and the structure checks, in the two sections above. **Every script-driven element on the WordPress page must map to a hook on the new page**: list the theme's own markers (an Alpine `x-data`, a slider library's classes) per page and confirm each has its module hook in the published HTML. A block with no hook compiles to markup that looks right and does nothing (a page menu that should stick, a share bar, tabs, a header search form).
4. **Console**: no errors on any page at any width (`scripts/console-check.mjs --all`; without the flag it loads every static page and one item of each collection).
5. **Links and media**: crawl staging (`scripts/crawl-links.mjs`): zero broken internal links; zero references to the local copy, and none to the old host in files a page loads (images, `srcset`, CSS backgrounds, embeds); canonical, `og:url` and JSON-LD identity URLs are meant to name the production domain and are allowed; then crawl again with requests to the old host blocked and confirm nothing visible breaks.
6. **URLs**: `scripts/check-urls.mjs` at zero failures.
7. **Content**: automated body comparison at 100% (`scripts/compare-bodies.mjs`), `scripts/glued-words.mjs --rendered` over every page, `scripts/leftover-text.mjs --all` and `scripts/colour-check.mjs --all` with nothing found. A side-by-side look at a sample of each type is a record for the reviewer, not a check. Any page whose markup an agent typed out by hand, not a compiler, gets a word-by-word comparison of its visible text with WordPress (same words, same order) before it is measured.
8. **SEO** (`scripts/seo-check.mjs`): exactly one `h1`; title and description equal the inventory; JSON-LD parses and holds the types the config asks for (validation is `verify-jsonld.mjs` and `schema-vocab-check.mjs`, in `structured-data.md`); the Open Graph image on **every** page and item is the picture WordPress prints there (none where WordPress prints none); sitemap lists what it should and nothing else. **Alt text**: the script checks that every image whose file has alt text in the inventory carries some; beyond that, compare per page by placement in the served HTML, keyed by file (strip WordPress size suffixes, `-scaled` and Webflow's asset-id prefix), leaving out hidden helper images, and with WordPress's own faults in mind: an alt cut short at a double quote, and a theme that prints the attachment title when alt is empty.
9. **Performance**: Lighthouse mobile on the home page, a media-heavy item, an article and the heaviest listing. Fix layout shift from fonts.
10. **Code parity**: see below.
11. **Editor acceptance**: through the Designer or Editor, change a hero, replace a gallery image, reorder a curated list, publish a new article, with no code change. The agent does it and records how; the owner repeats it at review. Then run the new-item test below.
12. **Reuse check**: `LEARNINGS.md` current, `site.config.json` holds every site value, scripts grep clean of site literals.

## Code parity: the check that finds what the others miss

Before calling a migration done, diff the old live site against the new one at the level of code, one page per template (`scripts/code-parity.py`): scripts by purpose, link tags, meta tags, JSON-LD types, noscript blocks, iframes. Then compare the tag manager container's triggers with the DOM hooks in the new markup, then HTTP behaviour.

On the reference migration this found what page-by-page visual and SEO checks had missed: no Open Graph or Twitter tags on any CMS template, a breadcrumb list the SEO plugin printed on every page, the form provider's tracking loader (which also carried the cookie banner), and root icon files.

Also check what fires before consent. Tag manager containers often load lead-tracking scripts with no consent setting; the rebuild inherits that unless someone decides otherwise. Report it; it is the owner's call.

## A check that did not run looks like a pass

On the third build two checks reported nothing wrong because they compared nothing. The share picture on item pages had never been compared (the SEO check looked at titles and descriptions; code parity confirmed the tag existed on static pages), and the structure check had been written for an earlier build's markers. Both were found late, one of them by a second session.

- **Every check prints what it compared**: how many pages, how many values. Zero compared is a failure, not a pass.
- **Every check compares a moved page with the same WordPress page.** A page whose address Webflow forces to change (a listing that shares its collection's folder, an old results address) has a rule in `pathRewrites`, and the sweep, the colour check, the heading check and the glued-words check all read it. Before they did, the sweep compared the moved news listing with the real one while two other checks compared it with WordPress's "not found" page, and their totals were quoted as if they covered it. A row that says `WordPress answered 404` or `fetch failed` is a fault in the page map, to fix before the count is quoted; it is not a result about the build.
- **The search results page is a page to build and to pair.** Give it the site's header, footer and main wrapper like any other page; nothing else in the phases asks for it, and one build's search page had none of the three. WordPress's results live at `/?s=<term>`, so pair the two by hand for the shell (header, footer, the heading) and expect the results themselves to differ: a site with no plan prints sample results until cutover.
- **A filter that passes a known fault is not evidence.** An audit with noise and shift filters reported no findings over 213 page states, one of which held a fault that two later checks both measured. Before trusting a clean result, seed a known fault and see the tool report it.
- **Say what share of the site a check covered.** "27 specs passed" reads like the site passed; it meant 27 pages and examples out of nearly 200. Any check that samples is followed by one that does not (for layout, the whole-page sweep).
- **Name the evidence for each "Done when" line by what was compared with what**, not by which script was run.
- **Have a session that did not do the build check the result** before hand-off, against pages saved from the live site at the start: every sitemap address answers on staging, and title, description, `h1` and share picture match per page. It needs only `curl` and the saved pages, and it is not anchored on the build's own reports.

## Test a new item the way an editor makes it

Imported items carry fields an editor will never fill: the WordPress id, a publish timestamp, a generated card excerpt. Create one new item by hand with only what an editor would enter (make it awkward: long title, no excerpt, no optional media), publish it, and look everywhere it should appear. On the reference migration this exposed:

- lists keyed or filtered by the WordPress id dropped the new item (slider picks, page de-duplication);
- stored "related" lists never included it;
- card text bound to an importer field was blank;
- a template title bound to an optional SEO field published an empty `<title>`;
- date ordering that relied on an importer timestamp put it in the wrong place;
- a card link bound to an importer-only address field was empty (let the script fall back to the collection's folder plus the slug);
- the share picture was empty, because the field behind it was optional.

The fixes generalise: key by link, not by importer id; compute related lists at view time from lists the template already holds; give card text a fallback (excerpt, else the first words of the body); make the fields a template cannot do without **required**; sort on the date editors fill, with Webflow's own order as the tie-break (an importer-only number as the first sort key sends every new item to the end: `import.md`). Then confirm the new item is on top wherever "newest" is promised, that grids still hold their shape with one more item, and that curated lists are unaffected. Delete the test item and confirm it is gone from listings, related lists, the sitemap (after a full publish) and search.

Tell editors what is automatic and what is not: automatic lists pick new items up on publish; curated lists never do; the sitemap needs a full site publish; search needs a reindex.

## Noise to recognise

- A one-line text wrap flipping at an exact breakpoint.
- The old site's fixed header covering click targets in tests.
- Differences confined to a slider or a lazy image, with equal page heights, have nearly always been a slider mid-transition or media not yet loaded, on either side. Confirm it before believing it: turn reduced motion on, force lazy images eager and measure again; then group what is left with its count, because one such group held a real fault.
- Headings inside slider tracks differ between slider libraries (one hides off-screen slides from assistive technology, another does not). Leave slider tracks out of the heading crawl and cover sliders with the block measurement and the behaviour suite.
- **`aria-hidden` sits on different elements on each side** (inactive slides, tab panels, hero slides). A text comparison that drops everything `aria-hidden` counts one slide on one side and every slide on the other, and one that keeps everything counts decoration. Drop only `aria-hidden` elements that hold no letters or digits, on both sides.
- Two slider libraries park their off-screen slides on opposite sides of the track (one wraps them to the left with negative x, the other keeps them to the right, clipped). Boxes differ, the visible slide does not: measure the visible slide.
- A listing that counts its active filters from every query parameter counts a cache-buster too ("All filters (1)"). The theme does the same; see "Cache-bust the Webflow side only".
- Links that sit side by side in the new markup with no whitespace between them (navigation, footer) read as one word in the raw HTML though they render apart. `scripts/glued-words.mjs --rendered` compares rendered text and does not trip on them (the raw mode flagged 171 pages for this alone). A map widget's own buttons can still read as one word there; leave them out with `checks.glued.skipWithin`.
- Staging and live HTML differ in compiled CSS names and Webflow attributes; strip the Webflow runtime tags and `data-wf-*` before comparing bodies.
- Map errors on staging when the key is restricted to the live domain: environment, not a regression.

## Browser testing gotchas

- **Click with the real pointer**, after scrolling the target into view. Script clicks hid a z-index bug.
- A slider sized before its parent changes width keeps old slide widths until a resize event. Set widths before init or dispatch resize.
- WebKit tabs only to form fields by default; use Option+Tab for link focus tests.
- `offsetParent` is null for fixed elements; use the bounding rect.
- Mobile WebKit has no mouse wheel; scroll by script.
- Check phone landscape (844×390, less about 230px of browser bars in Safari): menus that give a link list "the leftover height" collapse to nothing, sometimes on the old site too.
- Autoplay that stops on the last slide strands phones when the previous control is hidden. Copy the old slider's wrap behaviour.
- iOS Simulator screenshots lag taps by about a step; wait two or three seconds.
- **A simulator with no window draws no frames**, so composited transitions never finish and an autoplaying slider seems to stall after one move. Keep it drawing (recording the screen does it) while tests run.
- **A tap made by script carries no user gesture**: iOS refuses the clipboard, so check "Copy link" once with a real simulator tap. The simulator's clipboard syncs with the Mac's, so that tap overwrites the owner's clipboard: save and restore it.
- **The larger iPads send a desktop user agent** and the smallest sends a mobile one. A theme that picks markup on the server gives them different pages: read WordPress with each device's own user agent.
- **Several simulators at once make drags flaky.** Rerun a failed check alone before calling it a failure, and give each simulator its own ports.
- **A URL assertion read once races with the browser.** Wait for the address to change, with a short limit, before failing it.
- Test a bundle before releasing it: `scripts/bundle-swap.mjs` serves the unreleased build in place of the release on real staging pages. Serve everything the build loads by a path relative to itself, fonts included: with the stylesheet swapped and its font files answering 404, the fallback face moved lines by under a pixel and read as a regression that was not there.
- Re-run the whole behaviour suite after every release, not only the checks you think you touched.

## Accepted differences

Keep `verify/accepted-differences.md`: each difference with its reason. Any that loses content or behaviour needs the owner's yes.

- **The old site's own faults are not targets.** An image the editor's markup stretches to three times its height, a share button that never opens because of a typo in the theme, a theme helper that prints a broken video embed so a gallery switch shows an empty panel, focus rings hidden on every element: record each, do not copy it, and give the owner the list. Where the new site is better for a reason that matters (keyboard users can see where they are), say so.
- **Pasted formatting is content, not layout.** Editors' inline styles (a weight, a colour on a span) do not survive a rich-text field. Report them as content differences with a count and let the owner decide per site.
- **When one site shows a fault, check its sister sites for the same cause straight away**, read-only, by cause and not by page. On the third build a check of the two earlier sites, built with the same kit, found several of the same root causes on each, plus faults of their own.
